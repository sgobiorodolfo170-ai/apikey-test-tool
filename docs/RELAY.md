# 中转站说明

本地 OpenAI 兼容端点，把多个上游按模型名聚合转发。只监听 `127.0.0.1`，不做公网暴露。

## 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 探活，始终开放 |
| GET | `/v1/models`、`/models` | 聚合所有启用上游的模型与别名 |
| POST | `/v1/chat/completions`、`/chat/completions` | 对话，支持流式 |
| POST | `/v1/embeddings`、`/embeddings` | 向量 |

客户端 Base URL 填 `http://127.0.0.1:8787/v1`。默认端口 8787，可在界面修改（1024–65535）。

## 访问控制

- 默认不设置访问 Key，本机直接可用。
- 生成访问 Key 后，除 `/health` 与 `OPTIONS` 外都必须带 `Authorization: Bearer <key>`。
- 多客户端 Key：每把 Key 可命名，调用监控据此显示“客户端”，便于区分 Chatbox / Cherry Studio / SDK。
- 本地端点允许跨域，方便浏览器类客户端接入；仅限本机回环地址。

## 路由与故障转移

- 模型名精确命中某提供商 → 路由过去；别名（`客户端模型名=上游真实名`）会替换 `model` 后转发。
- 同名模型可配多个上游，按列表顺序优先；429 / 5xx / 网络错误自动切下一个。
- 4xx（429 除外）不重试，原样透传——重试不会让错误请求变正确。
- 只有一个启用上游时，任意模型名都走它（透明代理）。
- 多个上游且模型未命中时，**没有填写模型列表的上游会作为兜底候选**（刚添加、尚未拉取模型时可直接使用）；明确列了模型但不匹配的上游不会被选中。
- 所有上游都有模型列表且未命中 → 404 `model_not_found`；全部上游不可达 → 502 `upstream_error`。响应头 `x-relay-provider` 标明实际服务的上游。

## 多 Key

- 一个上游可配多把 Key，请求按 Key 轮询；401/403 或本地限流时切换同上游下一把 Key。
- 每把 Key 是独立账号：额度、冷却、限流均按“提供商 + Key”分别计算。
- “拉取模型”会依次尝试各 Key，成功即返回。

## 限流与并发

- 每个上游可设并发上限（默认 4）、每分钟请求数（默认不限）、排队超时（默认 10s）。
- 并发满时排队；RPM 用尽或排队超时视为可重试，切下一个上游。
- 流式请求最多占用 `并发上限 - 1` 个槽位，始终给普通请求留一个。
- 全部上游被本地限流 → 429 `rate_limit_exceeded` + `Retry-After`。

## 冷却与熔断

网络错误、401/403、429、5xx 后按指数退避冷却（5s 起，最多 60s）；冷却期内跳过该 Key。全部冷却 → 503 `upstream_cooling` + `Retry-After`。

## 额度窗口（5 小时 / 7 天）

- 每个提供商可设滚动 5 小时与滚动周上限，按“请求次数”或“积分/墨点”计量。
- 按 Key 分别记账；某把 Key 触顶只跳过它，继续同家其它 Key 和下一个提供商。
- 全部 Key 触顶 → 429 `quota_exhausted`，`Retry-After` 为最早一笔用量滑出窗口的秒数，`error.skippedKeys` 给出被跳过的 Key 尾号。
- 用量写入 `relay-usage.json`，重启不清零；额度锁（5h / 7d）同样持久化，重启后不会继续打已耗尽的 Key。
- 只有被上游正常受理的调用才计数：400/401/403/429 与 5xx 不占“请求次数”额度。

## 429 撞墙判定

单次 429 只做短冷却。必须“连续 3 次、且相邻两次至少间隔 1 分钟”（可在表单调整）才认定该 Key 额度窗口用尽：

- 第一次确认：暂停到 5 小时窗口重置；
- 解锁后再次撞墙：升级为 7 天锁。

这样既不被瞬时限流误判，也不会 5 秒后继续反复撞上游。

## 会话粘性

默认关闭。开启后按以下顺序取会话标识，把同一会话优先固定到同一个上游 Key：

1. `x-session-id` / `x-conversation-id` 请求头
2. 请求体的 `user` / `conversation_id`
3. 前两条消息的哈希

命中的候选只调整到队首，故障转移链保持完整。

## 缓存

- 默认关闭，仅缓存非流式成功响应。
- 键为 `model + 原始请求体`，TTL 可调；命中返回 `x-relay-cache: hit`。
- 命中时重写响应 `id` / `created`，避免跨会话看到同一条消息。
- 响应体超过 2MB（捕获截断）不写缓存，防止缓存残缺内容。

## 日志与统计

- 请求日志：时间、模型、实际上游、客户端、状态码、耗时、Key 尾号、是否故障转移、tokens 用量；最多 200 条。
- 调用监控：按 `request_id` 合并同一请求的多次尝试，展示尝试成功率与请求成功率；客户端主动取消记为 499，不计入上游失败。
- 统计：按 Key（提供商 + 尾号）与按模型汇总输入/输出/合计 tokens。
- 数据持久化到 `userData/relay-usage.json`，随应用启动恢复。

## 客户端配置

- OpenAI SDK：`baseURL = "http://127.0.0.1:8787/v1"`，`apiKey` 填访问 Key；未设访问 Key 时填任意非空值。
- Chatbox / Cherry Studio：Base URL 同上，模型选择 `/v1/models` 返回的任一模型。
- 浏览器页面接入：可直接 `fetch`，端点已允许跨域。

## 故障排查

| 现象 | 排查 |
|---|---|
| 404 `model_not_found` | 模型名不在任何上游列表；先拉取模型，或只启用一个上游 |
| 401 `invalid_api_key` | 已设置访问 Key，客户端未带或带错 |
| 429 `rate_limit_exceeded` | 本地并发/RPM 触顶；看调用监控的排队与 RPM |
| 429 `quota_exhausted` | 该提供商所有 Key 的窗口额度用尽；等 `Retry-After` 或换 Key |
| 502 `upstream_error` | 所有上游不可达；看日志里的状态码与错误 |
| 503 `upstream_cooling` | 所有上游在冷却；等 `Retry-After` |

**商汤网关**：`https://token.sensenova.cn/v1` 对未列出的字段较严格（如 `response_format`、`thinking`）可能返回无具体原因的 400；先关闭客户端的 JSON 模式/思考参数再试。

## 已知限制

- 仅支持 OpenAI 兼容的对话与 embeddings；不支持 Responses、图片生成、语音。
- 修改端口需先停止服务（运行中修改会提示先停止）。
- 配置热更新只对部分字段生效；以界面提示与 `electron/relay.cjs` 的 `update()` 为准。
