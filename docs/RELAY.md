# 中转站说明

本地 OpenAI 兼容端点，把多个上游按模型名聚合转发。默认只监听 `127.0.0.1`；可选开启局域网访问（必须先设访问 Key，见下文「局域网访问」）。不做公网暴露。

## 端点

| 方法 | 路径                                        | 说明                                             |
| ---- | ------------------------------------------- | ------------------------------------------------ |
| GET  | `/health`                                   | 探活，始终开放                                   |
| GET  | `/v1/models`、`/models`                     | 聚合所有启用上游的模型与别名                     |
| POST | `/v1/chat/completions`、`/chat/completions` | 对话，支持流式                                   |
| POST | `/v1/messages`、`/messages`                 | Anthropic 协议对话，转换为 OpenAI 上游，支持流式 |
| POST | `/v1/responses`、`/responses`               | 可选能力，暂未启用，返回 501                     |
| POST | `/v1/embeddings`、`/embeddings`             | 向量                                             |

客户端 Base URL 填 `http://127.0.0.1:8787/v1`。默认端口 8787，可在界面修改（1024–65535）。

## 访问控制

- 默认不设置访问 Key，本机直接可用。
- 生成访问 Key 后，除 `/health` 与 `OPTIONS` 外都必须带 `Authorization: Bearer <key>`；Anthropic 客户端默认发 `x-api-key: <key>`，服务端两种写法都接受。
- 多客户端 Key：每把 Key 可命名，调用监控据此显示“客户端”，便于区分 Chatbox / Cherry Studio / SDK。
- 本地端点允许跨域，方便浏览器类客户端接入。
- **非回环请求必须带 Key**：即使没设默认访问 Key，来自局域网（非 `127.0.0.1` / `::1`）的请求也会被拒绝；只有本机回环地址才允许免鉴权。开启局域网访问因此必须先设访问 Key（见下文）。

## 路由与故障转移

- 模型名精确命中某提供商 → 路由过去；别名（`客户端模型名 → 上游真实名`）会替换 `model` 后转发。
- 同名模型可配多个上游，按列表顺序优先；429 / 5xx / 网络错误自动切下一个。
- 4xx（429 除外）不重试，原样透传——重试不会让错误请求变正确。
- 只有一个启用上游时，任意模型名都走它（透明代理）。
- 多个上游且模型未命中时，**没有填写模型列表的上游会作为兜底候选**（刚添加、尚未拉取模型时可直接使用）；明确列了模型但不匹配的上游不会被选中。
- 所有上游都有模型列表且未命中 → 404 `model_not_found`；全部上游不可达 → 502 `upstream_error`。响应头 `x-relay-provider` 标明实际服务的上游。

### 默认上游（defaultProviderId）

- 在界面「默认上游」下拉里选定一个上游后，**模型名未命中任何上游时回退到它**，而不是直接 404；命中具体模型时仍按上面的精确/别名规则路由，默认上游不参与。
- 走默认路由的响应同样带 `x-relay-provider`，请求日志记 `routedBy: default`，便于区分「精确命中」与「默认兜底」。
- 默认上游被**禁用**或**没有可用 Key**时返回明确的 503 `default_provider_unavailable`，不会静默切到其它未授权上游。
- 「设为默认」只写 `defaultProviderId` 这一个字段，不改动任何凭据；留空即恢复「未命中即 404」的旧行为。
- `/v1/models` 始终广播**所有启用上游**的模型与别名，不受默认上游影响。

## 多 Key

- 一个上游可配多把 Key；401/403 或本地限流时切换同上游下一把 Key。
- 默认每把 Key 是独立账号：真实 429 锁定、冷却、限流均按“提供商 + Key”分别计算。
- **共享账号组（组件化）**：API Key 区域提供组管理组件，可新建、重命名、删除组，并显示每个组已加入的 Key 数；每行 Key 右侧的下拉把该 Key 加入某个组，留空为「未分组」。
- 共享组**只绑定当前提供商**：不同上游即使组名相同也不会合并；同一提供商内同组 Key 共享真实 429 锁定，冷却仍按 Key 隔离。
- **按模型隔离锁定**：真实 429 属于哪个模型，就只锁该 Key 的哪个模型；同 Key 的其它模型继续用真实请求探测，不会因为一个模型被限就整把 Key 停用。
- “拉取模型”会依次尝试各 Key，成功即返回。

## 限流、并发与多 Key 调度

- 每个上游可设并发上限（默认 4）、每分钟请求数（默认不限）、排队超时（默认 10s）。
- 并发满时排队；RPM 用尽或排队超时视为可重试，切下一个上游。
- 流式请求最多占用 `并发上限 - 1` 个槽位，始终给普通请求留一个。
- 全部上游被本地限流 → 429 `rate_limit_exceeded` + `Retry-After`。
- **真实状态调度**：开启自动额度保护后，同上游的多把 Key 按真实状态做平滑加权轮询（SWRR）：
  - 已被真实 429 锁定的 Key 权重为 0，不再参与调度；
  - 刚解锁、正在半开探测的 Key 先按 20% 流量，成功后再线性恢复；
  - 其余 Key 等权轮询，不再根据预估用量扣减权重；
  - 全部 Key 都被锁定时才退回轮询，由上层返回 429；
  - 关闭自动保护时保持原来的普通轮询，行为不变。

## 冷却与熔断

网络错误、401/403、429、5xx 后按指数退避冷却（5s 起，最多 60s）；冷却期内跳过该 Key。全部冷却 → 503 `upstream_cooling` + `Retry-After`。

- 429 的冷却取 `max(5s, 上游 Retry-After)`，上游要求等更久时不会被 5 秒后再次打爆；`Retry-After` 同时透传给客户端。
- 429 响应体若明确是额度耗尽（如 `insufficient_quota` / `quota_exhausted`），直接进入额度锁定，不再等多次确认（商汤例外，见下文「商汤网关」）。

## 自动额度保护（真实调用驱动）

额度不再按积分、请求次数或墨点预设计算；本地不做任何用量预估，只根据真实请求结果决定是否锁定：

- **真实成功即恢复**：任何一次 2xx 成功都会清除该 Key × 模型的锁定、确认点和升级等级。
- **真实 429 才锁定**：普通连续 429 先锁 5 分钟做探测；探测请求仍 429 升级 5 小时；5 小时后真实探测仍 429 升级 7 天。
- **上游明确额度耗尽**（如 `quota_exceeded` / `insufficient_quota`）时跳过 5 分钟探测，直接锁 5 小时；5 小时后仍失败再升级 7 天。商汤 429 速率/额度同码、无法区分，不适用本条。
- **分钟级限流不锁额度**：429 响应明确是 `rate_limit` / `too_many_requests` 时只走短冷却，不进入额度锁定。
- **按 Key × 模型隔离**：哪个模型收到真实 429，就只锁该模型；同 Key 的其它模型继续用真实请求探测。
- **共享账号组**：同组 Key 共享真实 429 锁定，但仍各自用自己的真实响应确认恢复。
- **持久化**：锁定与升级等级写入 `relay-usage.json`，重启后不会继续打已确认耗尽的 Key；任何一次成功都会清掉等级。
- 全部 Key 都被锁定 → 429 `quota_exhausted`，`Retry-After` 为最早解锁的 Key，`error.skippedKeys` 给出被跳过的 Key 尾号。

## 429 判定

单次 429 只做短冷却。普通 429 必须「连续 3 次、且相邻两次至少间隔 1 分钟」（可在表单调整）才认定该 Key 的额度窗口用尽：

- **第一次确认**：锁 5 分钟做真实探测，不直接锁 5 小时；
- **探测仍 429**：升级 5 小时锁；5 小时后真实探测仍 429，升级 7 天锁；
- **明确额度耗尽**：上游响应体明确是 `quota_exceeded` / `insufficient_quota` 时，直接锁 5 小时（商汤例外：其 429 只有一个 `quota_exceeded_error` 码，速率与额度同码，一律走连续确认 + 探测升级）；
- **观察窗**（默认 9 分钟）：超过这个跨度仍未凑齐的 429 视为不同事件，隔几天来的孤立 429 不会误锁；
- **突发判定**（可选，默认关闭）：高频持续 429 达到设定次数也可直接确认，覆盖客户端以小于 1 分钟间隔重试的情况；
- **半开恢复**：锁到期后先放 20% 流量做探测，成功后再在「渐进」分钟内线性恢复；探测再次 429 则按上一等级继续升级。

这样既不被瞬时限流误判，也不会因为本地预估把仍可用的 Key 提前停掉。

## 会话粘性

默认关闭。开启后按以下顺序取会话标识，把同一会话优先固定到同一个上游 Key：

1. `x-session-id` / `x-conversation-id` 请求头
2. 请求体的 `user` / `conversation_id`
3. 前两条消息的哈希

命中的候选只调整到队首，故障转移链保持完整。

## 缓存

- 默认关闭，仅缓存非流式成功响应。
- 键为 `model + 原始请求体`，TTL 可调；命中返回 `x-relay-cache: hit`。
- 命中时重写响应 `id` / `created`，避免跨会话看到同一条消息。
- 响应体超过 2MB（捕获截断）不写缓存，防止缓存残缺内容。

## 日志与统计

- 请求日志：时间、模型、实际上游、客户端、状态码、耗时、Key 尾号、是否故障转移、tokens 用量；保留最近 3 天（极端高频时最多 20000 条兜底）。
- 调用监控：按 `request_id` 合并同一请求的多次尝试，展示尝试成功率与请求成功率；客户端主动取消记为 499，不计入上游失败。
- 统计：按 Key（提供商 + 尾号）汇总输入/输出/合计 tokens；token 图表支持时 / 日 / 周 / 月。
- 数据持久化到 `userData/relay-usage.json`，随应用启动恢复。

## 诊断日志与长期观察

「诊断日志」选项卡分为两层数据：

- **事件日志**：启动/停止、配置变更、额度锁定与恢复、限流、上游失败等运行事件；保留 30 天，最多 10000 条。
- **提供商观察**：按「提供商 + 模型 + 自然日」聚合真实调用，保留 180 天，专门用于摸清商汤 / 端砚等上游的“脾气”：
  - 调用量、成功率、429（限流 / 额度锁定）、鉴权失败、4xx、5xx、网络错误、取消；
  - 延迟总和 / 最大值 / 分桶（<100ms、<500ms、<2s、<8s、<30s、≥30s）与慢请求占比；
  - 真实 usage tokens、0-23 点调用与 429 分布（识别高峰时段）；
  - 5 分钟探测 / 5 小时 / 7 天锁定次数、真实成功恢复次数与平均恢复时长。
- 观察数据随 `relay-usage.json` 持久化，重启不清零；面板支持 7 / 30 / 90 / 180 天范围、提供商与模型筛选，并可「复制 JSON」带走分析。
- 升级前没有观察数据时，会先用仍保留的 3 天请求日志回填一次，之后持续累计。

## Anthropic 协议（/v1/messages）

- `/v1/messages`（及 `/messages`）接受 Anthropic 格式请求，内部转换为 OpenAI `chat/completions` 复用同一套路由、故障转移、额度保护与日志，再把上游响应转回 Anthropic 格式。
- 支持非流式与流式：流式时把上游 OpenAI SSE 逐块转换为 Anthropic 事件序列（`message_start` → `content_block_start` → `content_block_delta` → `content_block_stop` → `message_delta` → `message_stop`）。
- 请求映射：`system`（字符串或文本块数组）→ system 消息；`max_tokens` / `temperature` / `top_p` / `stop_sequences` 对应转换；文本与图片（base64）内容块均可转发。
- 响应映射：`stop_reason` 按 `stop→end_turn`、`length→max_tokens`、`tool_calls→tool_use` 归一；`usage` 换算为 `input_tokens` / `output_tokens`。
- **当前边界**：暂不支持 `tool_use` / `tool_result` 工具调用块；上游若返回工具调用，文本部分仍会转发，但工具结构不做完整还原。需要完整工具链时请直接用 OpenAI 兼容端点。
- 上游错误（4xx/5xx）按原状态透传，不做 Anthropic 包装，便于客户端按真实错误处理。

## 局域网访问

- **默认关闭**，只监听 `127.0.0.1`。在界面勾选「局域网访问」后改为监听 `0.0.0.0`，同一网络内的其它设备可调用。
- **开启前必须设置访问 Key**（默认 Key 或任一客户端 Key）：未设 Key 时主进程拒绝启动（`LAN_KEY_REQUIRED`），界面也会拦截并提示。非回环请求无 Key 一律拒绝。
- **风险提示**：局域网内任何拿到 Key 的设备都能消耗你的上游额度，请只在可信网络中使用，并妥善保管 Key。
- 监听地址与端口一样**不能热切换**：运行中改动会提示「需停止并重新启动中转站后生效」。
- 界面列出可用局域网端点（`http://<网卡 IP>:<端口>/v1`，点击复制）；地址列表**过滤虚拟网卡**（VMware / VirtualBox / Hyper-V / Docker / WSL / 回环等），**物理网卡优先**排序。
- 客户端 Base URL 改用对应局域网 IP；`/v1/models`、鉴权、路由行为与本机一致。

## 客户端配置

- OpenAI SDK：`baseURL = "http://127.0.0.1:8787/v1"`，`apiKey` 填访问 Key；未设访问 Key 时填任意非空值。
- Anthropic SDK / Claude Code：`baseURL = "http://127.0.0.1:8787"`（Anthropic 客户端会自动补 `/v1/messages`），`apiKey` 填访问 Key（SDK 默认以 `x-api-key` 头发送，可直接使用）；模型名填 `/v1/models` 返回的任一模型。
- Chatbox / Cherry Studio：Base URL 同 OpenAI，模型选择 `/v1/models` 返回的任一模型。
- 浏览器页面接入：可直接 `fetch`，端点已允许跨域。
- 局域网接入：把上面的 `127.0.0.1` 换成界面给出的局域网 IP，并务必带上访问 Key。

## 故障排查

| 现象                               | 排查                                                               |
| ---------------------------------- | ------------------------------------------------------------------ |
| 404 `model_not_found`              | 模型名不在任何上游列表；先拉取模型，或只启用一个上游               |
| 401 `invalid_api_key`              | 已设置访问 Key，客户端未带或带错                                   |
| 429 `rate_limit_exceeded`          | 本地并发/RPM 触顶；看调用监控的排队与 RPM                          |
| 429 `quota_exhausted`              | 该提供商所有 Key 的窗口额度用尽；等 `Retry-After` 或换 Key         |
| 429 直接透传商汤错误               | 最后一个候选收到 429；看响应头 `Retry-After`，本地已按它冷却该 Key |
| 502 `upstream_error`               | 所有上游不可达；看日志里的状态码与错误                             |
| 503 `upstream_cooling`             | 所有上游在冷却；等 `Retry-After`                                   |
| 503 `default_provider_unavailable` | 默认上游被禁用或无可用 Key；启用它/补 Key，或取消默认上游          |
| 501 `not_implemented`              | 请求了 `/v1/responses`；该能力未启用，改用对话或 `/v1/messages`    |
| 启动提示「端口已被占用」           | 端口被其它程序占用；按提示改用替代端口，或先停止占用进程           |
| 局域网无法启动                     | 未设访问 Key；先生成访问 Key 或添加客户端 Key 再开启               |

**商汤网关**：`https://token.sensenova.cn/v1`（需完整保留 `/v1`），Bearer 鉴权。官方 429 只有一个错误码 `quota_exceeded_error`，同时表示「速率/额度超限」（2026-11 官方文档），建议指数退避重试——中转站因此对商汤不做「明确额度耗尽直接锁 5 小时」的跳级：所有 429 一律按连续确认进入 5 分钟探测，再按需升级 5 小时 / 7 天。网关对未列出的字段较严格（如 `response_format`、`thinking`）可能返回无具体原因的 400，先关闭客户端的 JSON 模式/思考参数再试；模型 ID 已对照官方文档核实，预置列表不含官方已下线的 `deepseek-v4-pro`。若频繁出现「429 确认额度耗尽」，先确认同账号的多把 Key 是否填进了同一个共享组，以及各模型的「按模型上限」是否高于官方额度。

## 已知限制

- 对话支持 OpenAI 兼容端点与 Anthropic `/v1/messages`（文本/图片，暂不含工具调用块）；embeddings 仅 OpenAI 兼容。Responses（返回 501）、图片生成、语音暂不支持。
- 修改端口需先停止服务（运行中修改会提示先停止）；局域网监听地址同样需重启生效。
- 配置热更新只对部分字段生效；以界面提示与 `electron/relay.cjs` 的 `update()` 为准。

## 网络与代理

- 中转站对上游的调用使用 Node `http`/`https` **直连**，不经过系统代理，因此上游链路天然不受代理影响。
- 测试页的网络请求走 Electron/Chromium 网络栈（`net.fetch`），遵循系统代理与其 bypass 设置。
- `NO_PROXY` / `no_proxy` 的绕过判定由 `electron/lib/net.cjs` 的 `resolveProxyBypass` 提供（支持 `*`、精确主机与后缀匹配），并有独立单测；当前用于直连链路的绕过判断，不覆盖 Chromium 的系统代理解析。
- 启动失败按错误类型给出可操作提示：`EADDRINUSE` 提示端口占用并给出替代端口；`EACCES`/`EPERM` 提示权限不足（不建议改用管理员权限运行）。
